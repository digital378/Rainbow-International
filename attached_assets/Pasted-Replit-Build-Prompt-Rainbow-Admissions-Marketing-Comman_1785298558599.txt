0. What you are building (one-paragraph summary)

Build a production-grade, mobile-first web application called "Rainbow Admissions Command Center" that captures school-admission walk-in enquiries through QR-code-driven branded forms, stores them in a reliable, validated database (not loose spreadsheets), auto-mirrors the data into Google Sheets for Academic Year 2027–28, and displays everything on fresh, creative, live dashboards at new URL slugs. The system serves two completely separate brands — Rainbow International School (RIS) and Rainbow International Pre-School (RPS) — which must never share logos, colours, data, or dashboards. The core goal is to eliminate the data-entry errors (wrong date formats, deleted cells, overwritten fields, broken formulas) that happen today when branches type directly into shared spreadsheets.

1. Background & problem being solved

Today, each branch types leads directly into shared Google Sheets. This causes recurring, expensive problems that this app must structurally prevent:

Inconsistent dates — the same column mixes 16-Jun-25, 2025-10-30, and 2025-11-08.
Broken phone numbers — random country codes, and two numbers jammed into one cell (9773254922/ 9082114342).
Manually typed "Month" column that is often wrong (an October date tagged "Sep-25").
Overwritten / shifted cells — e.g. a child's-name cell that literally reads "CLOSED".
Broken dashboards — summary tabs full of #REF! and #DIV/0! because a human edited a formula cell.

Design principle: humans should never again type free-form into a structured data field, and no one except the system should be able to write to the record of truth. Every value is captured through validated inputs; every record is immutable-by-default with a full change history.

6. Validation rules (this is the heart of the fix — implement strictly)

Apply on the client (instant feedback) and re-validate on the server (never trust the client):

Phone: accept digits only; strip spaces, +, -, /, and a leading 91/0; the result must be exactly 10 digits and start 6–9 (Indian mobile). Reject anything else with a clear inline message. Store the clean 10-digit value. If a user tries to enter two numbers, the second goes into the separate altPhone field.
Duplicate detection: on submit, if the same phone already exists for the same brand in AY 27-28, show a non-blocking warning ("This number already enquired on {date} for {program} at {branch}") and let staff choose View existing or Create anyway (a sibling/second child is valid). Log the decision.
Email: optional; if present, must match a standard email pattern; lowercase-normalize.
Dates: date-picker input only — no typed date strings. Store as real dates. enquiryDate defaults to today and cannot be in the future. walkInDate/revisitDate cannot be before enquiryDate.
Month: auto-derived from enquiryDate; not shown as an input; always correct.
Names: required, trimmed, title-cased for display; min 2 chars.
Program / Source / Status / Close reason / Branch / Lead owner: dropdowns bound to the lookup tables — impossible to enter an off-list value.
Required-field gating: the submit button stays disabled until all required fields are valid.
No destructive actions for staff: staff can never delete a record or edit a locked field (brand, enquiryDate, createdBy). "Delete" = archive (soft), reversible only by Admin, always logged.
7. The QR walk-in capture experience

Who uses it: front-desk staff on a tablet/kiosk at each branch reception, the moment a parent says "I want to enquire."

How it's reached: a printed QR code per brand (and optionally per branch — see §8) that opens the branded capture form. The QR points to the brand's capture URL.

Form screens (kiosk mode):

Branded welcome / start screen — brand logo, brand-colour background, a warm trust-first line (e.g. RIS: "Welcome to Rainbow International School — let's begin your enquiry." / RPS: "Welcome to Rainbow International Pre-School — happy beginnings start here."), and a big "Start Enquiry" button.
Capture form — large, touch-friendly fields in this order: Branch (pre-selected if per-branch QR) · Parent's Name · Child's Name · Phone · Alternate Phone (optional) · Email (optional) · Program (brand-specific dropdown) · Source (how did you hear about us) · Lead Owner (staff picking up the enquiry) · Enquiry Date (defaults today, editable via picker) · Remark (optional). Status defaults to OPEN; walk-in/revisit dates are set later from the admin/leads view, not on the kiosk.
Confirmation screen — "Enquiry saved ✓", shows a summary, then auto-resets to the welcome screen after ~6 seconds (or a "New Enquiry" button) so the next parent can be served. Never expose the previous parent's data to the next.

Kiosk safeguards: a short staff PIN (or logged-in staff session) to open the form so it can't be abused by passers-by; the form only writes, never lists/searches other leads.

On submit: write to Postgres → append the change to the audit log → the record instantly appears on the dashboards → queue the Google Sheets mirror sync.
